# Spec Guidelines

These are the rules every spec and plan must follow. Items marked **[lint]** are enforced by `sdd spec lint` or by plan validation, and an approval is refused while any of them fails. Items marked **[warn]** produce warnings only.

## Project Layout

```
<project>/
  sdd.yaml
  specs/
    <feature>/            # kebab-case, e.g. user-signup
      functional.md       # Phase 1: WHAT and WHY
      technical.md        # Phase 1: HOW
      plan.md             # Phase 2: groups and tasks
  .sdd/
    templates/            # project copies of the templates (customizable)
    profiles/             # language best-practice profiles (customizable)
    features/<feature>/   # state, journal, sessions, report
```

- One directory per feature. Feature names are kebab-case, unique and stable, because they are used in branch names (`sdd/<feature>`). **[lint]**
- Cross-feature dependencies are declared in the frontmatter (`depends_on: [other-feature]`), not by copying content.
- Keep a feature small enough that its plan has roughly 3 to 8 groups. Split larger work into several features. **[warn]**

## ID Conventions

| ID | Defined in | Meaning |
|---|---|---|
| `FR-###` | functional.md | Functional requirement |
| `NFR-###` | functional.md | Non-functional requirement (performance, security, …) |
| `AC-###` | functional.md, under an FR | Acceptance criterion |
| `ADR-###` | technical.md | Design decision |
| `G#` | plan.md | Task group |
| `T#.#` | plan.md | Task (`T<group>.<n>`) |

- IDs are unique within a feature and are **never reused or renumbered**. Retire an ID by striking it through (`~~FR-004~~ (removed)`) rather than deleting it. **[lint]**
- Number IDs with three digits, sequentially, in order of creation. **[lint]**
- Outside its feature, an ID is referred to as `<feature>/<ID>`.

## Functional Spec (`functional.md`)

Describes **what** the system must do and **why**. It does not describe how.

Required sections **[lint]**:
1. Summary
2. Problem & Goals
3. Non-Goals
4. Users & Scenarios
5. Functional Requirements
6. Non-Functional Requirements
7. Constraints
8. Open Questions
9. Glossary

Rules:
- Each `FR-###` is a single testable statement using "must" or "should". **[lint: ID format]**
- Each FR has at least one `AC-###` written as **Given / When / Then**. **[lint]**
- Each NFR is measurable, with a number and a unit where possible (e.g. "p95 < 200 ms"). **[warn]**
- **Open Questions must be empty before approval.** **[lint]**
- No implementation details such as framework names, table names or code. **[warn: keyword heuristics]**
- Use the Glossary terms consistently across both specs.

## Technical Spec (`technical.md`)

Describes **how** the approved functional spec will be built.

Required frontmatter **[lint]**:
```yaml
language: go               # selects .sdd/profiles/<language>.md
functional_hash: <sha256>  # filled in automatically on approval
commands:
  build: go build ./...
  lint: go vet ./...
  test: go test ./...
  integration: go test -tags=integration ./...
```

Required sections **[lint]**:
1. Overview
2. Architecture
3. Components
4. Data Model
5. Interfaces / APIs
6. Requirement Traceability
7. Error Handling
8. Testing Strategy
9. Decisions
10. Risks

Rules:
- The **Requirement Traceability** table maps every `FR-###` and `NFR-###` to one or more components. **[lint]**
- The **Testing Strategy** maps every `AC-###` to a test level (unit, integration or e2e). **[lint]**
- Every significant choice is recorded as `ADR-###` with Context, Decision and Consequences.
- Layers named in Architecture should match the layers used by the plan. **[warn]**

## Plan (`plan.md`)

Generated by the agent and reviewed by the user. Its structure is fixed so that it can be parsed:

```markdown
## G1: <group title>
- layer: domain
- depends_on: []
- goal: <one sentence>

### T1.1: <task title>
- covers: [FR-001, AC-001]
- files: [internal/order/order.go, internal/order/order_test.go]
- done_when: <observable completion condition>
- verify: <how to check it, normally a unit test name or pattern>

<short description of the change>
```

Rules **[lint]**:
- Groups are ordered by layer, and `depends_on` only references earlier groups. The dependency graph is acyclic.
- Every `FR-###` and `AC-###` is covered by at least one task.
- Each task touches at most `limits.max_files_per_task` files (default 5).
- Every task lists `covers`, `files`, `done_when` and `verify`.
- Unit tests for a task live in the same group as the task.

## Tests and Traceability

Every test that verifies an acceptance criterion references it, either in its name or in a comment, so that `sdd trace` and `sdd sync check` can find it:

```go
// covers: AC-003
func TestSignup_RejectsDuplicateEmail(t *testing.T) { … }
```

## Approval and Sync Rules

- Approval records the approver (from `git config user.name/email`), the time, and the SHA-256 of the artifact.
- Editing an approved artifact sends it back to drafting. Every artifact downstream of it becomes **stale** (see [WORKFLOW.md](WORKFLOW.md#staleness-rule)).
- `sdd sync check` must pass before any approval.

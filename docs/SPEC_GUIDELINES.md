# Spec Guidelines

These are the rules every spec and plan must follow. Items marked **[lint]** are enforced by `sdd spec lint` or by plan validation, and an approval is refused while any of them fails. Items marked **[warn]** produce warnings only.

## Project Layout

```
<project>/
  sdd.yaml
  specs/
    <feature>/            # kebab-case, e.g. user-signup
      functional.md       # Phase 1: WHAT and WHY
      technical.md        # Phase 1: HOW
      plan.md             # Phase 2: groups and tasks
  .sdd/
    templates/            # project copies of the templates (customizable)
    profiles/             # language best-practice profiles (customizable)
    features/<feature>/   # state, journal, sessions, report
```

- One directory per feature. Feature names are kebab-case, unique and stable, because they are used in branch names (`sdd/<feature>`). **[lint]**
- Cross-feature dependencies are declared in the frontmatter (`depends_on: [other-feature]`), not by copying content.
- Keep a feature small enough that its plan has roughly 3 to 8 groups. Split larger work into several features. **[warn]**

## ID Conventions

| ID | Defined in | Meaning |
|---|---|---|
| `FR-###` | functional.md | Functional requirement |
| `NFR-###` | functional.md | Non-functional requirement (performance, security, …) |
| `AC-###` | functional.md, under an FR | Acceptance criterion |
| `ADR-###` | technical.md | Design decision |
| `G#` | plan.md | Task group |
| `T#.#` | plan.md | Task (`T<group>.<n>`) |

- IDs are unique within a feature and are **never reused or renumbered**. Retire an ID by striking it through rather than deleting it: `### ~~FR-004~~ (removed)` for a requirement, `- ~~AC-007~~ (removed)` for a criterion. Each approval records the IDs it approved, so an approved ID that later disappears is reported. **[lint]**
- Number IDs with three digits, sequentially, in order of creation. Malformed IDs (`FR-1`) and gaps in the numbering are reported. **[lint]**
- Every ID that is referenced must be defined. Referencing a retired ID is a warning. **[lint]**
- Outside its feature, an ID is referred to as `<feature>/<ID>`.

## Functional Spec (`functional.md`)

Describes **what** the system must do and **why**. It does not describe how.

Required sections **[lint]**:
1. Summary
2. Problem & Goals
3. Non-Goals
4. Users & Scenarios
5. Functional Requirements
6. Non-Functional Requirements
7. Constraints
8. Open Questions
9. Glossary

Rules:
- Each `FR-###` is a level-3 heading `### FR-###: <title>` followed by a single testable statement using "must" or "should". **[lint: heading and ID format; warn: must/should]**
- Each FR has at least one `AC-###` bullet (`- **AC-###:** Given …, when …, then …`) written as **Given / When / Then**. An AC may continue on indented lines. **[lint]**
- Each NFR is measurable, with a number and a unit where possible (e.g. "p95 < 200 ms"). **[warn]**
- NFRs are bullets (`- **NFR-###:** …`) or level-3 headings under Non-Functional Requirements.
- **Open Questions must be empty before approval.** HTML comments and a bare "None" or "N/A" count as empty. **[lint]**
- Template placeholders such as `<requirement title>` must be replaced. **[lint]**
- No implementation details such as framework names, datastores or code blocks. **[warn: keyword heuristics]**
- Use the Glossary terms consistently across both specs.

## Technical Spec (`technical.md`)

Describes **how** the approved functional spec will be built.

Required frontmatter **[lint]**:
```yaml
language: go               # selects .sdd/profiles/<language>.md
functional_hash: <sha256>  # filled in automatically on approval
commands:
  build: go build ./...
  lint: go vet ./...
  test: go test ./...
  integration: go test -tags=integration ./...
```

`build`, `lint` and `test` are required **[lint]**; an empty `integration` command is a warning, because `sdd validate` then runs no integration tests. A missing `.sdd/profiles/<language>.md` is a warning.

Required sections **[lint]**:
1. Overview
2. Architecture
3. Components
4. Data Model
5. Interfaces / APIs
6. Requirement Traceability
7. Error Handling
8. Testing Strategy
9. Decisions
10. Risks

Rules:
- The **Requirement Traceability** table maps every `FR-###` and `NFR-###` to one or more components. **[lint]**
- The **Testing Strategy** maps every `AC-###` to a test level (unit, integration or e2e). Several levels may be listed, separated by commas or slashes. **[lint]**
- Both tables are read from their first column (one or more IDs) and second column (comma-separated components or levels). **[lint]**
- Every significant choice is recorded as `### ADR-###: <title>` with Context, Decision and Consequences. **[warn]**
- Layers named in Architecture should match the layers used by the plan. **[warn]**

## Plan (`plan.md`)

Generated by the agent and reviewed by the user. Its structure is fixed so that it can be parsed:

```markdown
## G1: <group title>
- layer: domain
- depends_on: []
- goal: <one sentence>

### T1.1: <task title>
- covers: [FR-001, AC-001]
- files: [internal/order/order.go, internal/order/order_test.go]
- done_when: <observable completion condition>
- verify: <how to check it, normally a unit test name or pattern>

<short description of the change>
```

Rules **[lint]**:
- Groups are numbered `G1, G2, …` in order, and tasks `T<group>.<n>` from 1 within their group.
- Every group lists `layer`; `depends_on` and `goal` are expected **[warn]**. Groups are ordered by layer: returning to an earlier layer is a warning.
- `depends_on` only references earlier groups, so the dependency graph is acyclic.
- Every `FR-###` and `AC-###` is covered by at least one task, and tasks cover only defined, non-retired FR, NFR and AC IDs. An uncovered NFR is a warning.
- Each task touches at most `limits.max_files_per_task` files (default 5).
- Every task lists `covers`, `files`, `done_when` and `verify`.
- Unit tests for a task live in the same group as the task.

## Tests and Traceability

Every test that verifies an acceptance criterion references it, either in its name or in a comment, so that `sdd trace` and `sdd sync check` can find it:

```go
// covers: AC-003
func TestSignup_RejectsDuplicateEmail(t *testing.T) { … }
```

## Approval and Sync Rules

- Approval records the approver (from `git config user.name/email`), the time, the SHA-256 of the artifact, the hashes of its sources and the IDs it defines. It is journaled as a `spec.approve` or `plan.approve` action.
- Approving the technical spec or the plan first stamps the current source hashes into its frontmatter.
- Editing an approved artifact sends it back to drafting. Every artifact downstream of it becomes **stale** (see [WORKFLOW.md](WORKFLOW.md#staleness-rule)).
- The sync checks that apply to an artifact must pass before it is approved: spec ↔ spec for the technical spec, spec ↔ plan (coverage) for the plan. An artifact can only be approved once its sources are approved and current.

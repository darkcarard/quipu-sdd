Quipu

Build from the spec with sdd

A quipu is the Inca record of knotted cords, where each knot is a fact tied to the rest. Quipu ties every requirement to its design, tasks, commits and tests. Your coding agent writes the specs, the plan and the code. You approve each step. sdd checks everything, commits the work and keeps a record of who did what.

What it is

One binary, four phases, no surprises

Quipu is a command-line tool, sdd, that runs next to the coding agent you already use. Every change to your project starts as a feature: a written spec of what it must do, a technical design, a plan split into small tasks, and only then code. Each phase ends at a gate that only a person can open.

Uses your subscription

The reasoning comes from Claude Code, under your own plan. sdd is deterministic and works offline.

Humans hold the gates

Approvals are not available to the agent. Its permission rules and a hook deny them, even inside wrappers like bash -c, and sdd rejects them when they come from the agent. You approve in your terminal (sdd approve G1), or with ! sdd approve G1 inside Claude Code.

Every line is traceable

Requirement → design → task → commit → test. sdd trace FR-001 shows the whole chain.

The workflow

Four stations, with a gate at each

A feature moves left to right. The agent drafts what is in each station; the amber gates are yours. If an approved document changes later, sdd flags everything that depends on it as stale.

Set up · once

Install, initialize, connect

You need Go 1.25, git and a coding agent: Claude Code, Codex CLI or Antigravity CLI. Pick yours and the manual adapts its commands. Install the binary once per machine; set up each project with sdd init. It only creates missing files and never changes one you already have.

A · per machine

Install sdd

$ go install github.com/darkcarard/quipu-sdd/cmd/sdd@latest
$ sdd version

It installs to ~/go/bin. Make sure that folder is on your PATH. You can also clone the repository and run make install. To update, run the same command, then sdd init --agent claude again in each project: it adds the files that are new in that release and leaves yours alone.

B · per project

Initialize the project

$ cd my-project
$ sdd init --agent claude
$ git add -A
$ git commit -m "Set up sdd"

Adds sdd.yaml, templates and your agent's files: the /sdd-* skills, the MCP server and the hook that keeps approvals yours. Set up several agents with a comma-separated list (--agent claude,codex). The repository needs at least one commit before implementing.

C · per project

Open Claude Code

$ claude
# approve the "sdd" MCP server
> /mcp

Claude Code asks once to approve the sdd server. /mcp should list it as connected, and typing / shows the /sdd-* skills. Run sdd commands in a terminal, or with ! inside Claude Code.

$ codex
# trust the project when asked
> /mcp
> /hooks

Codex reads .codex/ only in trusted projects. /mcp lists the sdd server, /hooks lets you review and trust the hook that keeps approvals yours, and typing $ shows the $sdd-* skills. Run sdd commands in a separate terminal.

Your first feature

From an idea to validated code

Keep two windows open: Claude Code, where the agent works, and a terminal, where you approve. Replace <f> with the feature name sdd gives you; sdd status lists them.

1

Describe what you want

The agent creates the feature, asks you questions and writes the functional spec: requirements (FR-001), non-functional requirements (NFR-001) and testable acceptance criteria (AC-001). sdd turns your description into a short, safe feature name.

in Claude Code
> /sdd-spec A to-do list CLI: add, list and complete tasks stored in a JSON file
in your terminal
$ sdd status
$ sdd spec lint <f>
$ sdd spec approve <f> --functional
2

Agree on the design

The technical spec records the architecture, decisions (ADR-001), which component covers each requirement, and the build, lint and test commands sdd will run to verify the code.

in Claude Code
> /sdd-tech <f>
in your terminal
$ sdd spec approve <f> --technical
Check that the verification commands are real, e.g. go build ./... and go test ./....
3

Approve the plan

The plan splits the work into groups (G1, G2…) of small tasks (T1.1…), each touching a few files. sdd sync check fails if any requirement or criterion is left uncovered.

in Claude Code
> /sdd-plan <f>
in your terminal
$ sdd sync check <f>
$ sdd plan approve <f>
4

Implement, one group at a time

You start the implementation; sdd creates an isolated worktree on branch sdd/<f>. The agent works through the group and stops when it is ready for your review. sdd review opens each changed file side by side in your editor (VS Code, VSCodium, Cursor; without one it prints the diff), and before that the /sdd-review skill can have a reviewer check the group against the criteria, the language profile and your project's rules. Approve it to continue, or send it back with feedback.

in your terminal
$ sdd implement <f>
in Claude Code
> /sdd-implement <f>
in Claude Code · optional
> /sdd-review G1      # expert review, writes a report
in your terminal, per group
$ sdd review G1          # side by side in your editor
$ sdd approve G1
# or send it back:
$ sdd revise G1 -m "Handle the empty file case"
agentsddyou
task_next→ write code→ task_done→ build · lint · test↺ next task
group_verify→ one commit with SDD trailers→ sdd-review (optional)→ sdd review→ approveorrevise→ /sdd-implement

If a check fails, the agent gets the failing output and fixes it, up to limits.max_fix_attempts times (3 by default). Run /sdd-implement <f> again after each approval until every group is done. Inside Claude Code, run the sdd commands with a leading ! (! sdd approve G1); /sdd-implement is a slash command and takes no !.

5

Validate and close

sdd runs the integration tests, checks that every group has its commit and every acceptance criterion has a test (a covers: AC-001 comment), and writes the report. Optionally, ask the agent for a semantic review against the criteria.

in your terminal
$ sdd validate <f>
$ sdd trace --matrix <f>
$ sdd merge <f>
in Claude Code · optional
> /sdd-deep-review <f>
sdd merge merges branch sdd/<f> into the branch checked out in your project, from any directory, removes the worktree and commits the feature's records. Prefer a pull request? Merge it your way, then run sdd merge <f> anyway: it sees the work is already there and only records it.
Existing projects

Adopt code you already have

For a project that already has code, start by documenting it. sdd adopt builds a short inventory (languages, build files, likely commands, tests), and the agent writes baseline specs from it. Your code is not touched. Baseline features have no plan; new work then starts as normal features on top of them.

in Claude Code
> /sdd-adopt
# or one area at a time:
> /sdd-adopt billing
in your terminal
$ sdd spec approve <f> --functional
Where things live

Everything is a file in your repo

Specs, plans, state and the audit journal are committed with your code, so the history travels with the project: sdd commits a feature's specs/<f>/ and .sdd/features/<f>/ on every approval and on sdd merge, and nothing else you have staged. Worktrees, locks and run logs stay local and are ignored through .sdd/.gitignore.

log.md is a readable version of the journal: every step, who ran it (you, or agent:claude-code) and when.

my-project/ ├─ sdd.yaml # limits and settings ├─ specs/ │ └─ todo-cli/ │ ├─ functional.md # what │ ├─ technical.md # how │ └─ plan.md # tasks ├─ .sdd/ │ ├─ templates/ profiles/ │ ├─ features/todo-cli/ │ │ ├─ state.json # phase, approvals │ │ ├─ journal.jsonl # audit trail │ │ ├─ log.md │ │ └─ report.md │ └─ worktrees/ # local only ├─ .mcp.json └─ .claude/ skills/ agents/ settings.json

Commands at a glance

Every command also has --help. The agent reaches the same functions through the sdd MCP server; the commands marked you are never available to it.

sdd status [<f>]anyonePhase of each feature and the next action.
/sdd-spec · /sdd-tech · /sdd-planagentDraft the functional spec, the technical spec, the plan.
sdd spec approve <f> --functional|--technicalyouFreeze a spec at its current content and commit the feature's records.
sdd plan approve <f>youFreeze the plan.
sdd implement <f>youCreate the worktree and start the first group.
/sdd-implement <f>agentWork through the current group until it is ready for review.
/sdd-review G1agentOptional expert review of the group (criteria, language profile, project rules); writes a report.

When something goes wrong

Common situations

I don't know where I am

Run sdd status <f>. It shows the phase, the state of every document and the exact next command.

Claude Code closed in the middle of a task

Run sdd resume <f> in your terminal, then /sdd-implement <f> again. The journal knows which step was running.

I edited a spec after approving it

The approval no longer matches. sdd sync check shows what is stale; review the change and approve it again.

The agent says it cannot approve

That is by design. Run the approval yourself in a terminal.

The MCP tools don't show up

Check that which sdd finds the binary, then restart Claude Code in the project folder and approve the server.

A group keeps failing its checks

After the fix attempts run out, the group is marked failed and the agent stops. Check sdd status <f>, then send guidance with sdd revise G1 -m "…" (the failed group).
